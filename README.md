# Что говорят покупатели — сводка отзывов в Telegram

Скрипт берёт свежие отзывы, через Gemini раскладывает их по темам и тону и раз в неделю присылает команде в Telegram короткую сводку: где жалоб стало больше, на что именно жалуются (с цитатами) и что хвалят. Читается за пару минут.

![Схема решения](docs/architecture.svg)

## Как выглядит сводка

Реальная сводка на тестовых данных (в Telegram заголовки выделены жирным):

```
📊 Отзывы за 18–24 окт
28 отзывов (было 20) · ★ 3.3 (было 3.9)
👍 8 · 👎 10 · ⚖️ 9 · 😐 1

Что изменилось
🆕 Приложение и прошивка: 6 жалоб, неделей раньше не было
📈 Доставка: 7 жалоб (было 1)
🆕 Упаковка и комплектация: 2 жалобы, неделей раньше не было
📉 Шум: 1 жалоба (было 4)
📉 Средняя оценка 3.3 (было 3.9)

🔥 Топ жалоб
1. Доставка — 7 (CM-2010 ×4, AF-5501 ×2, KT-3300)
   «„доставка за 3 дня“. Третью неделю жду» — CM-2010, ★1
   «на чайнике вмятина» — KT-3300, ★2
2. Приложение и прошивка — 6 (RV-0707 ×6)
   «приложение не видит пылесос» — RV-0707, ★1
...

💡 Обратить внимание
• 7 оценок ★1–3 ставят из‑за доставки или упаковки, а не товара
  (AF-5501, CM-2010, KT-3300). Это вопрос к логистике, а не к продукту
• RV-0707: главная претензия к товару — приложение и прошивка (6)
```

Дальше в сводке идут счётчики по всем темам с изменением к прошлой неделе и блок «Хвалят».

## Запуск

Нужен Python 3.10+ и около 10 минут, большая часть которых уходит на ключи.

```bash
git clone https://github.com/jul1zzZ/luxhomme-reviews.git && cd luxhomme-reviews
python -m venv .venv
.venv\Scripts\activate            # Linux/macOS: source .venv/bin/activate
pip install -r requirements.txt
copy .env.example .env            # Linux/macOS: cp .env.example .env
```

Что вписать в `.env`:

- `GEMINI_API_KEY` — ключ из [Google AI Studio](https://aistudio.google.com/apikey), бесплатного лимита хватает с запасом;
- `TELEGRAM_BOT_TOKEN` — создайте бота у [@BotFather](https://t.me/BotFather) командой `/newbot`;
- `TELEGRAM_CHAT_ID` — добавьте бота в чат, напишите туда что-нибудь, откройте `https://api.telegram.org/bot<TOKEN>/getUpdates` и возьмите `chat.id`. У группы id отрицательный, минус тоже нужен.

```bash
python -m review_digest run            # CSV → разметка → сводка в Telegram
python -m review_digest run --dry-run  # то же, но сводка печатается в консоль
python -m review_digest evaluate       # сверка разметки с ручным эталоном
```

Команды можно запускать и по шагам: `load --csv файл`, `classify`, `digest [--as-of 2026-10-24]`. Неделя — это 7 дней, заканчивающихся датой `--as-of`; по умолчанию берётся дата самого свежего отзыва. Для регулярной отправки `run` ставится в cron или Планировщик заданий на утро понедельника.

Тесты работают без сети и ключей: `pip install -r requirements-dev.txt && pytest`.

## Почему так и от чего я отказался

**Модель только размечает, считает код.** Можно было отдать LLM все отзывы и попросить написать сводку целиком. От этого я отказался: модель может ошибиться в подсчёте или «процитировать» то, чего никто не писал, а проверить это по готовому тексту трудно. Поэтому Gemini отвечает на узкий вопрос: какие темы в этом отзыве и с каким тоном. Числа, сравнение недель и выбор цитат — обычный код, который проверяется тестами.

**Фиксированный список тем, а не свободные теги.** Свободные темы модель на каждой неделе назовёт по-своему: «долгая доставка», «сроки», «логистика». Тогда сравнить неделю с неделей не получится. Список из 12 тем я составил по типичным претензиям к бытовой технике. Для того, что в него не попало, есть тема `other`, и сводка сообщает, если она начинает встречаться: значит, пора добавить тему.

**Тон определяется по каждой теме, а не по отзыву.** В «Кофе вкусный, но доставка 9 дней» есть и похвала товару, и жалоба на доставку. Если поставить отзыву одну метку «смешанный», жалоба на доставку пропадёт из подсчёта.

**Модель не видит звёзды.** Тон определяется только по тексту. Так видно, когда оценка и текст расходятся. На тестовой неделе 7 оценок от 1 до 3 звёзд поставлены только из-за доставки, к самому товару претензий нет. Если бы модель видела звёзды, она легко приписала бы негатив товару.

**Ответ модели проверяется.** Gemini отвечает по JSON-схеме, а код дополнительно проверяет каждую запись: знаком ли `review_id`, есть ли тема в списке, встречается ли цитата в тексте отзыва дословно. Непроверенные цитаты в сводку не попадают. Если модель пропустила отзыв, он отправляется повторно отдельно. При сбое API запрос повторяется с паузой: во время прогона Gemini дважды вернул 503, и повтор отработал. То, что так и не удалось разобрать, сводка показывает строкой «Не разобрано: N», а не теряет молча.

**SQLite и разметка с версией.** Запускается без настройки. Метки хранятся с версией «модель|промпт», поэтому повторный запуск не тратит запросы на уже размеченное. После смены промпта новая разметка ложится рядом со старой, и обе можно сверить с эталоном.

**Telegram через обычный HTTP-запрос.** Нужен один метод `sendMessage`, библиотека для ботов здесь лишняя. Длинная сводка режется по строкам, чтобы не разорвать HTML-разметку. Если Telegram вернул ошибку, URL в лог не пишется: в нём токен.

## Разбор

### Как я проверял, что AI не ошибается в темах

Все 48 отзывов я разметил вручную и специально добавил в выборку трудные случаи: сарказм («Ну да, конечно, „доставка за 3 дня“. Третью неделю жду»), отзыв из одного слова «Нормально», вмятина после доставки (это доставка или упаковка?) и сбой прошивки, из-за которого пылесос хуже убирает. Команда `evaluate` сравнивает разметку модели с эталоном и выдаёт таблицу всех расхождений.

Главная метрика — точность и полнота **жалоб**, то есть пар «отзыв + тема с негативом»: именно из них собирается топ сводки. Ложная жалоба опаснее пропущенной похвалы.

Что показал разбор расхождений:

1. **Первая версия промпта** расходилась с эталоном в 13 отзывах из 48. Примерно в половине случаев прав оказался не эталон, а модель: она следовала правилам из промпта, а ручная разметка им противоречила. Например, по правилу «норм» — это нейтрально, а в эталоне стоял плюс. Такие места я исправил в эталоне, всего 7, у каждого в колонке `note` указана причина.
2. **Настоящая ошибка модели:** упоминание для контекста она считала оценкой. Из «трещина на корпусе, коробка целая» получалось «упаковка — хорошо», из «хорошо хоть сам гриль целый» — «надёжность — хорошо». Во вторую версию промпта я добавил правило с этими примерами, и ошибки пропали.
3. **Спорное я оставил как есть.** «Отключается не докипятив. Брак» модель относит и к браку, и к качеству работы. Это граница между темами, а не ошибка.

| `gemini-3.6-flash`, итоговый эталон | v1 | v2 |
|---|---|---|
| Жалобы: точность / полнота | 97% / 100% | 97% / 100% |
| Темы: F1 | 97% | 99% |
| Тон по совпавшим темам | 99% | 99% |
| Общий тон отзыва | 96% | 94% |
| Цитаты найдены в тексте | 100% | 100% |

Общий тон отзыва от прогона к прогону колеблется на 2–4 пункта: модель путает «смешанный» и «негативный» на пограничных отзывах. На топ жалоб это не влияет, он строится по темам. Примеры в промпте (блендер, утюг, мультиварка) я намеренно взял не из тестовых отзывов, иначе модель «подсмотрела» бы ответы.

**Ограничения.** 48 отзывов — мало, и эталон размечал только я. Промпт писал тоже я, поэтому ошибки в эталоне и в правилах могут совпадать. Цифры выше показывают, что подход работает, но не гарантируют такую же точность на реальном потоке.

### Что я сделал бы иначе в продакшене

- **Источник.** Вместо CSV — API маркетплейсов: у Wildberries и Ozon есть методы для отзывов. Забирать раз в сутки, запоминать, до какого отзыва дошли.
- **Объём.** Десятки тысяч отзывов — это Batch API Gemini: дешевле и без лимитов на частоту запросов. Старую базу разметить один раз, дальше размечать только новые отзывы.
- **Качество.** Эталон из 200–300 отзывов, который независимо размечают два человека: если они сами расходятся, ждать от модели большего бессмысленно. Каждую неделю — 20 случайных отзывов на ручную проверку. Любую смену модели или промпта — сначала через `evaluate`.
- **Хранилище.** Postgres или DWH вместо SQLite, отдельная таблица тем, чтобы аналитики могли строить по ней дашборды.
- **Срочные сигналы.** Резкий всплеск жалоб на брак не должен ждать понедельника. Плюс алерт, если пайплайн упал или разобрал меньше 95% отзывов.
- **Сводка.** Разбивка по маркетплейсам и ссылки на сами отзывы, чтобы с ними можно было сразу работать.

### Вопросы маркетингу до старта

1. Что вы будете делать со сводкой? Если по ней ставят задачи продукту, нужна разбивка по SKU. Если спорят с маркетплейсом о логистике — по складам и регионам.
2. Какие темы вам важны? Свой список я составил с нуля. Если у поддержки уже есть категории обращений, лучше взять их: тогда отзывы и тикеты считаются одинаково.
3. Сколько отзывов приходит в неделю и с каких площадок? От этого зависят стоимость и способ обработки.
4. Кому нужна сводка: одна общая в чат или отдельные для продукта, логистики и поддержки?
5. Что считать тревогой, о которой надо сообщать сразу, а не в понедельник?
6. Отвечаете ли вы на отзывы? Та же разметка может подсказывать, кому и что ответить.
7. Есть ли уже размеченные данные, например тикеты поддержки по категориям? Это готовый эталон, гораздо больше 48 отзывов.

## Сверх задания

- Блок «Обратить внимание»: низкие оценки, в которых виновата логистика, а не товар; главная претензия по каждому SKU; отзывы, где оценка противоречит тексту; отзывы, не попавшие ни в одну тему.
- Проверка цитат: в сводку не попадает то, чего покупатель не писал.
- Версии промпта и сверка с эталоном: видно, что именно улучшила каждая правка.
